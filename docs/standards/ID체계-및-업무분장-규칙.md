# ID 체계 및 업무 분장 규칙

| 항목 | 내용 |
|---|---|
| 문서 번호 | STD-001 |
| 버전 | 1.1 (2026-10-02) |
| 적용 대상 | 신규 웹앱 개발 프로젝트의 기능 명세, 설계·개발 문서, 이슈, 커밋, 테스트 |
| 최초 적용 | [참고 사양서](../spec/02-참고사양서.md) 문서 버전 0.3 |

## 1. 목적

기능마다 하나의 ID를 부여해 **기획 → 설계 → 개발 → 테스트 → 운영** 전 과정에서 같은 기능을 같은 이름으로 추적한다. ID 앞글자만 보고 담당 업무를 알 수 있게 하고, 계층 번호만 보고 기능의 위치를 알 수 있게 한다.

## 2. 업무 분장 (접두어)

### 2.1 접두어 정의

| 접두어 | 업무 분장 | 담당 범위 | 예 |
|---|---|---|---|
| **F** | Frontend | 화면, 사용자 상호작용, 클라이언트 로직, 클라이언트 측 계산 | 편집기 모드, 배선 그리기, BOM 표, PDF 출력 |
| **B** | Backend | 인증, 권한 판정, 서버 API, 결제 연동, 외부 서비스 호출 | 로그인, 주문 생성, 공용 부품 API |
| **D** | Database | 도메인 데이터 모델, 서버 테이블, 브라우저 저장소, 파일 형식 | 프로젝트 모델, IndexedDB 스키마, `.ezc` 형식 |
| **I** | Infra·운영 | 호스팅·배포, 환경 설정, 기능 스위치, 보안 설정, 모니터링, 품질 검증 자동화 | CI, CSP, 기능 스위치, 사용 분석 도구 |
| **C** | Content·정책 | 법적 문서, 요금·상품 정책, 안내 문구, 샘플 데이터, 마케팅 미디어 | 이용약관, 요금제, FAQ, 샘플 프로젝트 |

### 2.2 분장 판단 기준

한 항목이 어느 분장인지 헷갈리면 아래 순서대로 판단한다.

| 순서 | 질문 | 예이면 |
|---|---|---|
| 1 | 코드가 아니라 문서·정책·데이터 자체인가? | **C** |
| 2 | 데이터의 구조·저장 형식을 정의하는가? | **D** |
| 3 | 서버에서 실행되거나 서버와의 약속(API)인가? | **B** |
| 4 | 기능이 아니라 기능을 돌리는 환경·절차인가? | **I** |
| 5 | 그 밖에 사용자가 보고 조작하는 것 | **F** |

**경계 사례**

| 항목 | 분장 | 이유 |
|---|---|---|
| 브라우저 IndexedDB 스키마 | D | 저장 위치가 아니라 "데이터 구조"가 기준이다 |
| 자동 저장 실행(타이머·트리거) | F | 저장 구조는 D, 저장을 일으키는 동작은 F |
| 클라이언트에서 거는 무료 한도 | F | 서버 판정은 B, 한도 수치 자체는 C |
| 기능 스위치 값 | I | 켜고 끄는 것은 운영 행위다 |
| UI 문구 사전(i18n) | 전환 기능은 F, 문구 자체는 C | 기능과 내용을 나눈다 |

### 2.3 여러 분장에 걸치는 기능

하나의 사용자 기능이 여러 분장에 걸치면 **분장별로 ID를 따로 부여**하고 **연관 ID**로 서로 연결한다.

```
결제 기능
├─ F09-03-02  결제 화면           (연관: B03-01-01, B03-02-01)
├─ B03-01-01  주문 생성 API       (연관: F09-03-02, D06-01-01)
├─ B03-02-01  PG 결제 요청        (연관: F09-03-02)
└─ D06-01-01  주문 테이블         (연관: B03-01-01)
```

- 연관은 **양방향**으로 적는다. 한쪽에만 적으면 반대쪽에서 찾지 못한다.
- 대표 ID는 사용자가 직접 만나는 쪽(보통 F)으로 한다.

## 3. ID 형식

### 3.1 구조

```
F 05 - 01 - 02
│ │    │    └─ 3계층: 개별 기능       (01~99)
│ │    └────── 2계층: 기능 묶음       (01~99)
│ └─────────── 1계층: 영역            (01~99)
└───────────── 접두어: 업무 분장       (F·B·D·I·C)
```

**형식:** `X00-00-00` — 접두어 1글자 + 계층별 2자리 번호 3개 + 하이픈(`-`) 구분자

### 3.2 계층

| 계층 | 형식 | 예 | 의미 | 단위 |
|---|---|---|---|---|
| 1계층 | `X01-00-00` | F05-00-00 | 대분류 | 업무 영역 (예: 배선) |
| 2계층 | `X01-01-00` | F05-01-00 | 중분류 | 기능 묶음 (예: 배선 생성) |
| 3계층 | `X01-01-01` | F05-01-02 | 개별 기능 | 개발·테스트 단위 (예: 분기 배선) |

### 3.3 번호 규칙

- 각 계층은 `01`~`99`를 쓴다.
- `00`은 "그 계층이 없음", 즉 상위 항목 자체를 뜻한다.
- 상위 계층이 `00`이면 하위 계층도 `00`이다. `F05-00-03`은 틀린 ID다.
- 두 자리를 고정하므로 문자열 정렬 순서가 계층 순서와 같다.
- 번호는 **추가한 순서대로** 부여한다. 화면 배치나 중요도 순서를 번호에 담지 않는다. 순서가 필요하면 문서 표에서 정렬한다.

### 3.4 검증용 정규식

```regex
^[FBDIC](0[1-9]|[1-9][0-9])-((0[1-9]|[1-9][0-9])-(0[0-9]|[1-9][0-9])|00-00)$
```

| 입력 | 결과 | 이유 |
|---|---|---|
| `F05-01-02` | 통과 | |
| `F05-01-00` | 통과 | 2계층 |
| `F05-00-00` | 통과 | 1계층 |
| `F05-00-03` | 실패 | 2계층 없이 3계층 |
| `F00-01-01` | 실패 | 1계층은 01부터 |
| `F5-1-2` | 실패 | 두 자리 고정 |
| `X05-01-02` | 실패 | 정의되지 않은 접두어 |

## 4. 표기 규칙

### 4.1 사용처별 표기

| 사용처 | 규칙 | 예 |
|---|---|---|
| **파일 내부** (본문, 표, 연관 열, 주석) | 항상 **전체 ID** | `F05-01-02` |
| **파일명·폴더명** | 상위 계층은 폴더가 나타내므로 **자기 계층 번호 + 이름** | `02-분기배선.md` |
| 이슈 제목 | `[전체 ID] 제목` | `[F05-01-02] 분기 배선 삭제 시 고아 데이터 발생` |
| 커밋 메시지 | `전체 ID: 요약` (여러 개면 쉼표) | `F05-01-02: 분기 배선 연쇄 삭제` |
| 브랜치 | `유형/전체ID-영문요약` | `feature/F05-01-02-branch-wire` |
| 테스트 이름 | `전체 ID 동작` | `F05-01-02 호스트 배선 삭제 시 분기 배선도 삭제` |
| 코드 주석 | 필요할 때만 `// F05-01-02` | 기능 경계가 불분명한 곳에 한정 |

전체 ID로 검색하면 문서·이슈·커밋·테스트가 한 번에 나와야 한다. 파일명만 예외다.

### 4.2 파일·폴더 구조

기능별 문서를 나눌 때 폴더가 상위 계층을 나타낸다.

```
docs/spec/
├─ F05-배선/                    ← 1계층 폴더: 접두어 포함 전체 1계층 ID + 이름
│  ├─ 00-개요.md                ← F05-00-00 영역 개요
│  ├─ 01-배선생성/              ← 2계층 폴더: 번호 + 이름
│  │  ├─ 00-개요.md             ← F05-01-00 묶음 개요
│  │  ├─ 01-단자간배선.md       ← F05-01-01
│  │  └─ 02-분기배선.md         ← F05-01-02
│  └─ 02-배선스타일/
│     └─ 01-색상팔레트.md       ← F05-02-01
└─ B03-주문결제/
   └─ ...
```

| 대상 | 규칙 | 예 |
|---|---|---|
| 1계층 폴더 | `접두어+번호-이름` | `F05-배선` |
| 2계층 폴더 | `번호-이름` | `01-배선생성` |
| 3계층 파일 | `번호-이름.md` | `02-분기배선.md` |
| 상위 항목 개요 | `00-개요.md` | `F05-배선/01-배선생성/00-개요.md` |

- ID 복원: 폴더 경로를 이어 붙인다. `F05` + `01` + `02` → `F05-01-02`
- 이름에는 공백을 쓰지 않는다. 한글은 허용한다.
- 문서 첫 줄 제목에는 반드시 전체 ID를 쓴다. 예: `# F05-01-02 분기 배선`
- 기능 수가 적으면 폴더를 나누지 않고 한 파일에 표로 관리해도 된다(참고 사양서 방식). 이때도 표 안에는 전체 ID를 쓴다.

## 5. 운영 규칙

### 5.1 부여

1. 분장을 정한다(2.2 판단 기준).
2. 들어갈 1계층·2계층을 찾는다. 맞는 곳이 없으면 새 2계층을 만든다. 새 1계층은 팀 합의 후에만 만든다.
3. 그 계층의 **마지막 번호 + 1**을 부여한다. 빈 번호를 메우지 않는다.
4. 기능 목록 표에 등록하고, 연관 ID를 양쪽에 적는다.

### 5.2 변경 금지 원칙

- **한번 부여한 ID는 바꾸지 않는다.** 기능 이름과 설명은 고쳐도 ID는 유지한다.
- **폐기한 번호는 재사용하지 않는다.** 폐기 기능은 상태를 `폐기`로 두고 행을 남긴다.
- 기능을 다른 계층으로 옮겨야 하면 새 ID를 발급하고, 옛 ID는 `폐기`로 두면서 비고에 `→ 새 ID`를 적는다.

### 5.3 분할과 병합

| 경우 | 처리 |
|---|---|
| 기능 하나를 둘로 나눔 | 기존 ID는 한쪽이 유지하고, 다른 쪽에 새 ID 부여. 비고에 `← 분할: 기존 ID` |
| 두 기능을 하나로 합침 | 한쪽 ID를 유지하고 다른 쪽은 `폐기`, 비고에 `→ 병합: 유지 ID` |
| 3계층 기능이 커짐 | 2계층으로 올리지 않는다. 새 2계층을 만들고 하위 기능을 새로 부여한 뒤 옛 ID는 `폐기` |

### 5.4 상태

| 상태 | 의미 |
|---|---|
| 계획 | 기능 목록에 등록, 착수 전 |
| 개발중 | 설계·구현 진행 중 |
| 완료 | 구현과 테스트 완료 |
| 보류 | 일정·우선순위로 중단 |
| 폐기 | 하지 않기로 결정. 번호 재사용 금지 |

참고 서비스 분석 문서처럼 "확인 여부"를 나타낼 때는 별도 기호(● ◐ ○)를 쓰고, 문서 첫머리에 정의한다.

### 5.5 변경 기록

ID를 새로 만들거나 폐기·이동·분할·병합할 때는 기능 목록 문서의 변경 이력에 남긴다.

| 날짜 | ID | 변경 | 사유 |
|---|---|---|---|
| 2026-10-01 | F05-01-04 | 신규 | 배선 경유점 스냅 추가 |
| 2026-10-05 | F05-03-04 | 폐기 | 배선 다발 기능 제외 |

## 6. 기능 목록 표 양식

### 6.1 기본 양식

```markdown
| ID | 기능 | 설명 | 상태 | 우선순위 | 연관 | 비고 |
|---|---|---|---|---|---|---|
| **F05-01-00** | **배선 생성** | | | | | |
| F05-01-01 | 단자 간 배선 | 단자에서 단자로 배선을 그린다 | 계획 | MVP | D01-02-03 | |
| F05-01-02 | 분기 배선 | 기존 배선 위의 점에서 분기한다 | 계획 | Beta | D01-02-04 | |
```

| 열 | 필수 | 내용 |
|---|---|---|
| ID | ● | 전체 ID. 1·2계층 행은 굵게 표시 |
| 기능 | ● | 짧은 기능 이름 |
| 설명 | ● | 한 줄 설명 |
| 상태 | ● | 5.4의 상태 |
| 우선순위 | | MVP / Beta / 이후 등 릴리스 단위 |
| 연관 | | 다른 분장의 연관 ID |
| 비고 | | 참고 위치, 분할·병합·이동 기록 |

필요하면 `담당자`, `참고`(참고 서비스 위치 등) 열을 추가한다.

### 6.2 기능 문서 머리말 (폴더로 나눌 때)

```markdown
# F05-01-02 분기 배선

| 항목 | 내용 |
|---|---|
| 상태 | 계획 |
| 우선순위 | Beta |
| 연관 | D01-02-04, F05-01-01 |
| 참고 | REF-SPEC-001 F05-01-02 |

## 설명
## 수용 기준
## 변경 이력
```

### 적용 점검표

- [ ] 모든 기능에 접두어가 맞게 붙었는가 (2.2 판단 기준)
- [ ] 여러 분장에 걸친 기능의 연관 ID가 양쪽에 적혔는가
- [ ] 상위 `00` 뒤에 하위 번호가 붙은 잘못된 ID가 없는가
- [ ] 파일 내부에서는 전체 ID, 파일명에서는 자기 계층 번호만 썼는가
- [ ] 폐기된 번호를 다시 쓰지 않았는가

## 부록 B. 참고 사양서 ID와의 관계

- 참고 사양서(REF-SPEC-001)의 ID는 **참고 서비스의 기능**에 붙인 번호다. 새 개발 프로젝트의 ID와 번호가 같더라도 같은 기능이라는 보장은 없다.
- 새 개발 프로젝트 기능이 참고 서비스 기능에서 왔다면 비고나 `참고` 열에 `REF-SPEC-001 F05-01-02`처럼 출처를 적는다.
